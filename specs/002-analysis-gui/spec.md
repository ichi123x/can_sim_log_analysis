**Feature Branch**: `002-analysis-gui`

**Status**: Draft

- Q: 起動方法は？ → A: B。コマンドで起動し、.canprj を引数で渡すと最初から開く。加えてダブルクリックで起動できるショートカット（またはバッチファイル）を用意する。単体の exe は作らない（FR-060a〜b）。

- /speckit-analyze 後の修正（2026-10-22）: 解析画面の大きさは MFC と同じく枠を含めたウィンドウ全体（FR-022）。解析中にアプリを閉じる要求は MFC と同じく受け付けず、届いたら中断して止まるのを待ってから閉じる（FR-016）。SC-002 の目盛りの比較は初期サイズ・同じ拡大率で行う。

## 概要

機能 001 で作った解析コア（MFC 版と同じ数値の表を作る部分）に、MFC 版と同じ操作の画面を付ける。
利用者はプロジェクトを開き、「解析」メニューから 4 つの解析画面（送信待ち時間、受信完了時間、送信ジッター、
CAN バス負荷）を開いて、表・注記・グラフで結果を見る。

画面の振る舞いは MFC 版（`reference/mfc/AnalysisDlg.cpp`、`MFCApplication1Dlg.cpp` の解析メニュー部分、
`MFCApplication1.rc`）に合わせる。元仕様（`Doc/CANログ解析ツール仕様.md`）と MFC 版が食い違うときは MFC 版に従う（憲章 原則 I）。
表の数値・文字列は機能 001 の解析コアをそのまま使い、画面で作り直さない（憲章 原則 II）。

範囲外: シミュレーションの実行、フレーム編集、ログ表示（MFC の「ログ表示」メニュー）、プロジェクトの保存、
解析結果の画面からの保存・印刷（CSV が要るときは機能 001 のコマンドラインを使う）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - プロジェクトを開いて送信待ち時間を見る (Priority: P1)

評価担当者がツールを起動し、「ファイル > プロジェクト読込み」で .canprj を選び、「解析 > 送信待ち時間」を選ぶと、
送信待ち時間の画面が開く。上に表（全体＋CAN ID ごと）、その下に注記 1 行、下にグラフ（選んだ行のヒストグラム）が出る。
開いたときは表の 1 行目（全体）が選ばれていて、そのヒストグラムが出ている。別の行を選ぶとグラフがその行に変わる。

**Why this priority**: 画面の骨格（メインウィンドウ、メニュー、プロジェクトを開く、解析画面の枠、表とグラフの連動）がすべてそろう最小の単位で、
MFC 版との見比べ（目視確認済みの送信待ち時間）でそのまま確かめられる。

**Independent Test**: `tests/data/sample_vehicle_16ecu` を開き、送信待ち時間の画面の表の全セルが機能 001 の正解 CSV（`golden/txwait.csv`）と一致すること、
行を選ぶとグラフが変わることを確かめる。

**Acceptance Scenarios**:

1. **Given** sample_vehicle_16ecu を開いた、**When** メインウィンドウを見る、**Then** ファイル名・パス・ログの有無と、通信速度、ECU 16 台の一覧、送信フレームの一覧（31 フレーム）が表示される（FR-004）。
2. **Given** ツールを起動した直後（プロジェクト未選択）、**When** 「解析 > 送信待ち時間」を選ぶ、**Then** 解析は行わず、
   「プロジェクトファイルがないため、シミュレーションログはありません。…」のメッセージが出る（AR-022、MFC IDS_LOG_NONE_NOPROJECT）。
3. **Given** sample_vehicle_16ecu を開いた、**When** 「解析 > 送信待ち時間」を選ぶ、**Then** タイトル「送信待ち時間 - sample_vehicle_16ecu.canprj」の画面が開き、
   表の 32 行（全体＋CAN ID 31 行）の全セルが `golden/txwait.csv` の 4 行目以降と一致し、注記が 2 行目と一致し、1 行目（全体）が選ばれている。
4. **Given** 送信待ち時間の画面、**When** 0x1A0 の行を選ぶ、**Then** グラフがその行のヒストグラム（0 µs に 50 件の棒 1 本）に変わる。
5. **Given** 送信待ち時間の画面が開いている、**When** もう一度「解析 > 送信待ち時間」を選ぶ、**Then** 新しい画面は開かず、開いている画面が前面に出る（AR-091）。
6. **Given** 送信待ち時間の画面、**When** Esc を押すか閉じるボタンを押す、**Then** 画面が閉じる。Enter では閉じない（AR-091）。

---

### User Story 2 - 受信完了時間と送信ジッターを見る (Priority: P2)

評価担当者が「解析 > 受信完了時間」「解析 > 送信ジッター」を選ぶと、それぞれの画面が開く。
受信完了時間は送信待ち時間と同じ形（表・注記・ヒストグラム）。送信ジッターは表・注記と、選んだ CAN ID のジッターの時系列グラフ
（横軸 送信開始の時刻 ms、縦軸 ずれ µs、0 の線付き、点を線で結ぶ）を出す。

**Why this priority**: US1 の枠に表の種類とグラフの種類を足すだけで作れ、遅延の評価に次いで使われるため。

**Independent Test**: sample_vehicle_16ecu で 2 つの画面の表が `golden/latency.csv`、`golden/jitter.csv` と一致し、ジッター画面で行を選ぶと時系列グラフが変わることを確かめる。

**Acceptance Scenarios**:

1. **Given** sample_vehicle_16ecu を開いた、**When** 「解析 > 受信完了時間」を選ぶ、**Then** 表と注記が `golden/latency.csv` と一致し、全体の行のヒストグラムが出る。
2. **Given** 同じプロジェクト、**When** 「解析 > 送信ジッター」を選ぶ、**Then** 表と注記が `golden/jitter.csv` と一致し、1 行目の CAN ID の時系列グラフが出る。
3. **Given** 送信ジッターの画面、**When** 送信 1 回だけ（件数 0）の CAN ID を選ぶ、**Then** グラフの場所に「データがありません」と出る。
4. **Given** 点の数がグラフの横幅（ピクセル数）より多い CAN ID、**When** その行を選ぶ、**Then** 横 1 ピクセルごとにその範囲の最小〜最大を縦線で描き、山も谷も消えない（AR-073）。

---

### User Story 3 - CAN バス負荷を見る (Priority: P2)

評価担当者が「解析 > CAN バス負荷」を選ぶと、上に要約 1 行、中央に 10 ms 区間ごとの負荷率の折れ線
（縦軸 0〜100%、平均を破線と「平均 N%」で表示）、下に ECU ごとの表が出る画面が開く（AR-084）。

**Why this priority**: 他の 3 画面と配置が違う（表が下、グラフが中央）ので別に作るが、価値は US2 と同程度。

**Independent Test**: sample_vehicle_16ecu で要約と ECU 表が `golden/busload.csv` と一致し、折れ線と平均の破線が出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** sample_vehicle_16ecu を開いた、**When** 「解析 > CAN バス負荷」を選ぶ、**Then** 要約が `golden/busload.csv` の 2 行目と一致し、ECU 表が 4 行目以降と一致する。
2. **Given** 同じ画面、**When** グラフを見る、**Then** 区間の数（500）が横幅より多くても、各列にはその範囲の最大値が描かれ、山が消えない（AR-084）。
3. **Given** 送信が 1 つもないログ、**When** 画面を開く、**Then** グラフの場所に「データがありません」と出る。

---

### User Story 4 - 大きなログでも固まらずに待てる・やめられる (Priority: P3)

評価担当者が数百万行のログで解析を選ぶと、0.5 秒を超えた時点で「解析中」ウィンドウ（文言と進捗バー、「中断」ボタン）が出て、
読み込みの進み具合がわかる。「中断」を押すと解析をやめ、解析画面は開かない。その間もメインウィンドウは固まらない。

**Why this priority**: 小さなログでは不要だが、実運用の大きなログで使えるために欠かせない（憲章 原則 IV、AR-033、AS-003）。

**Independent Test**: 300 万行の合成ログ（機能 001 の性能テストと同じもの）で、進捗ウィンドウが出ること、「中断」で止まること、その間メインウィンドウが再描画されることを確かめる。

**Acceptance Scenarios**:

1. **Given** 300 万行のログのプロジェクト、**When** 解析を選ぶ、**Then** 0.5 秒を超えたところで「解析中」ウィンドウが出て、「ログを読み込んでいます...」と進捗バー（読んだバイト数の割合）が出る。読み込みが終わると「集計しています...」になり、バーは満了になる。
2. **Given** 「解析中」ウィンドウ、**When** 「中断」（または Esc・閉じるボタン）を押す、**Then** 文言が「中断しています...」になり、ボタンは押せなくなり、止まったら「解析中」ウィンドウが閉じる。解析画面もメッセージも出ない（MFC と同じ）。
3. **Given** 0.5 秒以内に終わる小さなログ、**When** 解析を選ぶ、**Then** 「解析中」ウィンドウは出ずに解析画面が開く。

---

### User Story 5 - 開けない・読めないときに理由がわかる (Priority: P3)

評価担当者がログのないプロジェクトや壊れたログで解析を選ぶと、理由のメッセージが出て、解析画面は開かない。

**Why this priority**: 正常系の後でよいが、誤った表を出さないために必要。

**Independent Test**: 機能 001 の `tests/data/errors/` のプロジェクトで、それぞれのメッセージを確かめる。

**Acceptance Scenarios**:

1. **Given** .log.csv がないプロジェクトを開いた、**When** 解析を選ぶ、**Then** 「プロジェクト「no_log.canprj」のシミュレーションログはありません。…」のメッセージが出る（MFC IDS_LOG_NONE）。
2. **Given** 5 行目が壊れたログのプロジェクト、**When** 解析を選ぶ、**Then** 「シミュレーションログを読み込めませんでした。」とログのパスのメッセージが出て、解析画面は開かない（MFC IDS_LOG_READ_ERROR）。
3. **Given** INI として読めない .canprj、**When** 「プロジェクト読込み」で選ぶ、**Then** 読めない旨のメッセージが出て、それまで開いていたプロジェクトはそのまま残る。

### Edge Cases

- 解析画面を開いたまま別のプロジェクトを開いた: 開いている解析画面はすべて閉じる（MFC CloseResultWindows、028 FR-008）。
- 同じ解析を続けて選んだ: 2 つ目は開かず、開いている画面を前面に出す。解析もやり直さない。
- 解析画面を開いたあとでログが書き換わった: 開いている画面はそのまま（開き直せば新しいログで計算する）。
- 表の行が 0 件（送信なしのジッター）: 表は空で、グラフは「データがありません」。
- 全体の行が件数 0（ヘッダだけのログ）: 選ぶとグラフは「データがありません」。
- 値がすべて同じ行: ヒストグラムは幅 1 µs の棒 1 本。
- ウィンドウを小さくした: 最小 520×400（96 dpi 換算）より小さくできない（AR-092）。
- 高 DPI（125%、150%）の画面: 文字・余白・最小サイズが DPI に合わせて大きくなり、文字が切れない。
- 解析画面を開いた状態でメインウィンドウを閉じた: 解析画面も閉じてアプリが終わる。
- 解析中にアプリを閉じようとした: MFC 版と同じく閉じられない（最初の 0.5 秒はメインウィンドウが入力を受け付けず、その後は「解析中」ウィンドウがモーダルで出るので、先に中断するか終わるのを待つ）。それでも閉じる要求が届いたとき（Windows のサインアウトなど）は、解析を中断し、裏の処理が止まるのを待ってから閉じる（FR-016）。

## Requirements *(mandatory)*

### Functional Requirements

**メインウィンドウとメニュー（AR-090）**

- **FR-001**: アプリを起動するとメインウィンドウが開き、メニューバーに「ファイル(F)」と「解析(A)」を持たなければならない。
- **FR-002**: 「ファイル」には「プロジェクト読込み(O)...」（MFC と同じ表示名）と「終了(X)」を持つ。「プロジェクト読込み」は .canprj を選ぶファイル選択ダイアログを開く。
- **FR-003**: 「解析」の項目と並び順は MFC 版のリソースと同じとする: 「送信待ち時間(W)...」「受信完了時間(R)...」「送信ジッター(J)...」、区切り線、「CAN バス負荷(B)...」。
- **FR-004**: メインウィンドウには、いま開いているプロジェクトの情報と .canprj の内容を表示しなければならない（Clarifications Q1 = B）。
  - **FR-004a**: プロジェクトの情報: ファイル名、パス、ログの有無（あればログのファイル名と大きさ）。プロジェクト未選択なら「プロジェクトが開かれていません」の旨。
  - **FR-004b**: ネットワーク: 通信速度（[Network] BitRateBps）、ECU 数（[Project] EcuCount）、シミュレーション時間（[Project] DurationSec）。
  - **FR-004c**: ECU の一覧（[NodeN] ごと 1 行）: ノード番号、名前、ラベル、受信フィルタ（なければ「全受信」）、受信処理遅延、電源投入時刻、初期化時間。
  - **FR-004d**: 送信フレームの一覧（[NodeN.FrameM] ごと 1 行）: 送信 ECU、フレーム名、CAN ID（「0x080」形式）、DLC、周期、初回オフセット。
  - **FR-004e**: .canprj に項目がない・値が読めないときは、その欄を空欄にする（エラーにしない）。表示だけで、編集・保存はしない。解析の計算には使わない（元仕様 AR-003）。
- **FR-005**: プロジェクトを開いたら、開いている解析画面をすべて閉じなければならない（MFC CloseResultWindows）。
- **FR-006**: プロジェクトが読めない（存在しない、INI として読めない）ときはメッセージを出し、それまでのプロジェクトを保つ。

**解析の実行（AR-022、AR-033、MFC RunAnalysis）**

- **FR-010**: 「解析」の項目を選んだとき、プロジェクトが未選択なら IDS_LOG_NONE_NOPROJECT の文言、ログがなければ IDS_LOG_NONE の文言（プロジェクトのファイル名入り）を情報メッセージで出し、解析しない。文言は MFC 版のリソースのまま（2 文目の「開始」の案内も含む）。
- **FR-011**: 同じ解析の画面がすでに開いていれば、解析をやり直さずにその画面を前面に出す（AR-091）。
- **FR-012**: ログの読み込みと計算は画面とは別の処理として行い、その間も画面は応答し続けなければならない（憲章 原則 IV）。
- **FR-013**: 解析が 0.5 秒以内に終わらなければ、モーダルの「解析中」ウィンドウを出す。文言は読み込み中「ログを読み込んでいます...」、計算中「集計しています...」、中断を押した後「中断しています...」。進捗バーは読み込み中は読んだバイト数の割合、計算中は満了。ボタンは「中断」。
- **FR-014**: 「中断」・Esc・閉じるボタンで中断を指示し、処理が止まったら「解析中」ウィンドウを閉じ、解析画面もメッセージも出さない。中断を指示した後はボタンを押せなくする。
- **FR-015**: ログが読めなかったら、IDS_LOG_READ_ERROR の文言（「シミュレーションログを読み込めませんでした。」とログのパス）を警告メッセージで出し、解析画面は開かない。
- **FR-016**: 解析中はアプリを閉じる操作を受け付けない（MFC と同じ）。それでも閉じる要求が届いたときは、解析を中断し、裏の処理が止まるのを待ってから（最長で計算 1 回分。300 万行で約 3 秒）閉じる。解析画面が残っていれば、それも閉じる（MFC OnDestroy の CloseResultWindows）。

**解析画面の共通の振る舞い（AR-091〜AR-094）**

- **FR-020**: 各解析画面はモードレスの別ウィンドウで開く。メインウィンドウや他の解析画面と同時に操作できる。
- **FR-021**: ウィンドウタイトルは機能 001 の表の表題（例「送信待ち時間 - <プロジェクトのファイル名>」）と同じ。
- **FR-022**: 初期サイズは送信待ち時間・受信完了時間・送信ジッターが 900×640、CAN バス負荷が 960×680、最小サイズは 520×400。いずれもタイトルバーと枠を含めたウィンドウ全体の大きさ（MFC の `MoveWindow`・`ptMinTrackSize` と同じ）で、96 dpi 換算、DPI に合わせて拡大する。メインウィンドウの中央に出し、モニタの作業領域からはみ出さない。
- **FR-023**: Esc と閉じるボタンで閉じ、Enter では閉じない。
- **FR-024**: 表の列見出し・セルの文字列は、機能 001 の表（`latency_table` 等が作る Table）をそのまま表示する。数値の列（MFC で右寄せの列）は右寄せにする。行は 1 行ずつしか選べない。
- **FR-025**: 表のセル文字列は、同じログについて機能 001 のコマンドラインの出力（表 CSV）と完全に一致しなければならない。

**送信待ち時間・受信完了時間・送信ジッターの画面（AR-093、MFC LayoutListNoteGraph）**

- **FR-030**: 配置は、上に表（残りの高さの 2/5）、その下に注記 1 行、残りにグラフ。ウィンドウの大きさを変えると配置も追従する。
- **FR-031**: 開いたときは表の 1 行目を選び、その行のグラフを出す。行の選択を変えるとグラフをその行のものに変える。
- **FR-032**: 送信待ち時間・受信完了時間のグラフは、選んだ行の値のヒストグラム（機能 001 の `make_histogram`）。横軸「時間 (µs)」、縦軸「件数」。件数 0 の行は「データがありません」。
- **FR-033**: 送信ジッターのグラフは、選んだ CAN ID のジッターの時系列（横軸「時刻 (ms)」= 送信開始の時刻、縦軸「ずれ (µs)」）。0 の線を引き、点を線で結ぶ。点の数がグラフの横幅（ピクセル）より多いときは、横 1 ピクセルごとにその範囲の最小〜最大を縦線で描く（MFC MinMaxPerColumn）。件数 0 の行は「データがありません」。
- **FR-034**: 送信ジッターの注記は IDS_JIT_NOTE、送信待ち時間・受信完了時間の注記は OVERWRITE の件数入りの文言（機能 001 の Table.note）。

**CAN バス負荷の画面（AR-084、MFC CBusLoadDlg）**

- **FR-040**: 配置は、上に要約 1 行（機能 001 の Table.note）、中央にグラフ（残りの高さの 3/5）、下に ECU 表。
- **FR-041**: グラフは 10 ms 区間ごとの負荷率の折れ線（横軸「時刻 (ms)」、縦軸「負荷 (%)」、0〜100 を 20 ごとに目盛り）。区間の数が横幅（ピクセル）より多いときは、横 1 ピクセルごとにその範囲の最大値を描く（MFC MaxPerColumn）。平均を破線と「平均 N%」（N は小数 1 桁）で示す。送信がなければ「データがありません」。

**グラフの共通の描き方（MFC CAnalysisGraph）**

- **FR-050**: 軸の目盛りは MFC と同じ規則（1・2・5 × 10^m の刻み。MFC NiceTicks）で決め、目盛りの数値は整数なら整数で表示する。縦軸の名前は左上、横軸の名前は下中央に置く。
- **FR-051**: ヒストグラムの縦軸は 0 から始め、最大件数を含む目盛りまで。ジッターの縦軸は 0 を含み、最小〜最大を覆う目盛り（全部 0 なら −1〜1）。
- **FR-052**: グラフは表示内容（目盛りの刻み、軸の範囲、軸名、平均線、0 の線、間引き方）が MFC と同じであればよく、色・フォント・線の太さなどの見た目をピクセル単位で一致させることは求めない。行の高さの 1〜2 px の差や、件数の少ない棒の描き方の差なども、プロジェクトオーナーの判断（2026-10-23、VERIFIED.md）として合わせない。

**起動**

- **FR-060**: 利用者は次の 2 通りでアプリを起動できなければならない（Clarifications Q2 = B）。
  - **FR-060a**: コマンドで起動する。.canprj のパスを引数で渡すと、起動時にそのプロジェクトを開いた状態になる（開けなければ FR-006 と同じメッセージを出し、未選択の状態で起動する）。
  - **FR-060b**: エクスプローラーからダブルクリックで起動できるもの（ショートカットまたはバッチファイル）をリポジトリに用意する。起動時にコンソールの黒いウィンドウが残らない。
  - Python のない PC で動く単体の実行ファイルは作らない（範囲外）。
- **FR-061**: 画面の部品は機能 001 の解析コアに依存してよいが、解析コアは画面の部品に依存してはならない（機能 001 FR-039、憲章 原則 II）。

### Key Entities *(include if feature involves data)*

- **アプリの状態**: いま開いているプロジェクト（機能 001 の Project。未選択もある）と、開いている解析画面（種類ごとに 0 か 1 つ）。
- **プロジェクトの内容**: .canprj から読んだ表示用の値。ネットワーク（通信速度、ECU 数、シミュレーション時間）、ECU（ノード番号、名前、ラベル、受信フィルタ、受信処理遅延、電源投入時刻、初期化時間）、送信フレーム（送信 ECU、名前、CAN ID、DLC、周期、初回オフセット）。

- **解析画面**: 種類（送信待ち時間／受信完了時間／送信ジッター／CAN バス負荷）、機能 001 の解析結果と Table、選んでいる行。
- **グラフの内容**: ヒストグラム（機能 001 の Histogram）、ジッターの点の列、区間ごとの負荷率と平均。

## Assumptions

- 利用者は機能 001 と同じ評価担当者。Windows 11 で使う。
- 表の文字列・注記・表題・ヒストグラム・ジッターの点・区間ごとの負荷率は、機能 001 の解析コアが作るものをそのまま使う。画面のために解析を作り直さない。
- 機能 001 にない「グラフの間引き（MinMaxPerColumn、MaxPerColumn）」と「目盛り（NiceTicks）」は、MFC の LogAnalysis.cpp の同名の関数と同じ規則で、この機能で作る（機能 001 の contracts/core-api.md で画面機能に回したもの）。
- メニューの表示名と並びは MFC 版のリソース（`MFCApplication1.rc` の IDR_MAINMENU）に合わせる。元仕様 AR-090 の並び（受信完了時間、CAN バス負荷、送信待ち時間、送信ジッタ）は MFC のリソースと違うので、MFC に従う（元仕様 AQ-6 の解決）。「ファイル > 終了」は MFC にないが、元仕様 AR-090 にあるので足す。
- 文言（メッセージ、軸名、「データがありません」、「平均」、「解析中」ウィンドウ）は MFC 版のリソースをそのまま使う。
- ログが読めないときの詳しい理由（`line N: ...`）は、MFC 版と同じく画面には出さない（必要ならコマンドラインで確かめる）。
- 解析中に新しいプロジェクトを開く・別の解析を選ぶことはできない（「解析中」ウィンドウがモーダルのため。MFC と同じ）。
- 対象の画面の DPI は 100〜200%。
- メインウィンドウの .canprj 表示（FR-004）は、MFC 版のメインウィンドウがプロジェクトの ECU と送信フレームを表示していることに対応する。MFC 版はバス図と一覧を独自に描いているが、本ツールでは表で表示し、バス図・シミュレーションの状態表示・ログ欄は持たない。MFC にない指標や編集機能は足さない（憲章 原則 V）。
- .canprj の読み方は元仕様 AR-021 の形式（`[Project]`、`[Network]`、`[NodeN]`、`[NodeN.FrameM]`）に従う。値の単位は .canprj のまま（µs）で表示し、周期・時間を ms に直すかは plan で MFC のメインウィンドウ・編集画面の表示に合わせて決める。
- ダブルクリック用のショートカット（またはバッチファイル）は、リポジトリ内の `.venv` の Python を使う。`.venv` の作り方は機能 001 の quickstart と同じ。
